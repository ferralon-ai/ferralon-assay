# v0.4.0

This release adds a third verdict value, `indeterminate`, for a run that executed but established nothing, and tightens what counts as a reasoned `not_exploitable`. That change breaks compatibility for code that consumes the verdict vocabulary, so this is a minor release rather than a patch. It also stops `pr-inherit` from overwriting the stored baseline, treats SSH server input as attacker-controllable in Go, and stops Jinja-templated Python requirements files from producing junk SBOM entries.

Assay versions are `vX.Y.Z`: X is the product version, Y moves when a release breaks compatibility, and Z is a compatible increment.

### Breaking changes

Both changes are in the `verdict` package and the projections built on it. They affect code that imports Assay as a Go module and works with `verdict.PoE`. The scan `Report` that the CLI and the Action produce carries its own `report.Verdict` values, and its output does not change.

**A new verdict value.** `verdict.DirectionIndeterminate` and `verdict.StrengthIndeterminate` (both the string `indeterminate`) join the direction and strength sets. They always appear together: `Validate` rejects a PoE where one is indeterminate and the other is not. An indeterminate PoE may not carry a proof evidence flag, a `PatchValidation`, a `NonExploitableBasis`, a `Reproducer` or `ReasonedGrounds`. It may carry an `Objection`. `Label()` returns `indeterminate`, with no strength prefix.

If your code switches on `Direction`, `Strength` or `Label()`, add a case for `indeterminate`. Don't let it fall into a default arm that treats it as `not_exploitable`: it means nothing was established, not that the vulnerability is safe.

**A reasoned `not_exploitable` must now be grounded.** `Validate` rejects a PoE with direction `not_exploitable` and strength `reasoned` whose `NonExploitableBasis` is empty (`BasisNone`). If you produce that shape, either set the basis that grounds it (`version_not_in_affected_range`, `vulnerable_symbol_absent` or `static_refutation`), or, if nothing grounds it, emit `indeterminate` instead.

### How `indeterminate` projects

Every projection treats it as "needs follow-up", never as a clean result:

- SARIF: level `none`, kind `open`, and a message stating that no verdict was established and follow-up is required.
- SSVC: exploitation `none` and automatable `no`, so the outcome is `Track`. SSVC has no "unknown" impact tier, so technical and mission impact use the same floor as `not_exploitable` (`partial`, `low`). On the impact axes alone, an indeterminate verdict cannot be told apart from a grounded `not_exploitable`; the direction field and the exploitation and automatable axes carry the difference.
- The redacted PoE carries the direction through unchanged.

In the `corpus` fixture format, `indeterminate` is now a valid `expected_verdict.direction`. It is separate from the Assess-tier `undetermined` finding verdict, which means no reachability determination was made.

Outputs for `exploitable` and `not_exploitable` verdicts are unchanged.

### `pr-inherit` no longer writes the state store

When a pull request changed dependencies, `pr-inherit` re-analyzed the affected advisories and then stored the result in the same state ref the default branch's baseline lives in. The next PR inherited from that unmerged Report, and `cve-watch` diffed against it. On a fork, where the token can't write the ref, the same path failed the run.

`pr-inherit` now only reads the store. It still re-analyzes changed packages and publishes the merged Report, but it never stores it. The baseline stays owned by `baseline` and `cve-watch`, and `pr-inherit` runs the same on a fork as on a branch in the repository. No action is needed; the README and operator guide describe the new behavior.

### Go: SSH server input is an attacker-controllable ingress

The Go analyzer now recognizes a package-level function that takes a `golang.org/x/crypto/ssh` `ServerConn`, `ConnMetadata`, `NewChannel`, `Channel` or `Request` (including pointer and channel forms) as an `ssh` ingress. Those parameters seed taint, and a vulnerable symbol reached from such an ingress grades `attacker_tainted` rather than `control_flow_only`. Previously only net/http shapes counted, so a sink reached through an SSH handler graded `control_flow_only`.

`ssh.PublicKey` and `ssh.ServerConfig` are excluded because they also appear in trusted setup code. A path reached only from `main` still grades `control_flow_only`.

### Python: Jinja-templated requirements

A requirements line carrying a Jinja delimiter (`{`, `}` or `%`) is no longer read as a package. A templated name, such as a `{% if %}` control line, is skipped. A templated version, such as `pkg=={{ ver }}`, keeps the package with an unresolved version instead of a garbage literal. Pinned lines between template blocks still parse, so both branches of a conditional are kept. This applies to requirements files, `pyproject.toml` dependency lists and the selected-set resolver, which share one spec parser.

### Documentation

- A new [operator guide](../operator-guide.md) covers reading a Report, subject toolchain resolution, run modes and the state store, and which publish surface fires under which permissions, including on forks.
- The README's Advisory corpus section now documents `ASSAY_ADVISORY_CORPUS_DIR`, `ASSAY_ADVISORY_CORPUS_REQUIRED` and `-require-advisory-corpus`.
- For contributors: [AGENTS.md](../../AGENTS.md) and the [release process](README.md) state that releases are cut only by pushing a tag, and `scripts/build-release.sh` prints a reminder on a local `release` or `package` build that its output is not a published release (`ASSAY_LOCAL_BUILD=1` silences it).
