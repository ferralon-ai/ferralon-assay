# v0.4.1

This release makes the Action default to the v0.4 scanner, keeps a failed PR comment or dashboard Issue write from failing a finished scan, and records the advisory corpus manifest's provenance on the Report. Nothing here breaks an existing setup.

### Before you upgrade

**Move your Action pin.** `@v0.4` keeps fetching the latest v0.4 patch. To get this release, pin `uses: ferralon-ai/ferralon-assay@v0.4.1` (or that tag's commit SHA). If you set `scanner-sha256`, update it to the v0.4.1 tarball's checksum.

**The Action's `scanner-version` default is `v0.4`.** It was `v0.3`. Leave `scanner-version` unset to follow the v0.4 scanner. A workflow that sets it explicitly keeps the scanner it names, including a v0.3.x release: the Action links each analyzer under both `assay-plugin-<lang>` and `tegron-plugin-<lang>`, so a scanner released before v0.4.0 still finds its analyzers.

### A failed surface write no longer fails the scan

Before, if GitHub refused the sticky PR comment or the dashboard Issue (Issues disabled on the repository, a token without the scope) or failed to serve the write, the `assay` step exited 1 even though the scan had finished. A workflow couldn't guard against that with `continue-on-error` without also hiding real scan failures.

Now those two writes are best-effort. A failure logs a `::warning::` and adds a "Surfaces not updated" note under the scan headline in the job summary. The note names the surface and the HTTP status when GitHub answered. For a refusal (401, 403, 404 or 410) it also names the input that turns the surface off: `pr-comment` or `issue`. Any other 4xx reports the rejected write and its status without asserting a cause. The exit code comes from the scan and the local writes alone.

Only those two surfaces are best-effort, because they write to the repository through the GitHub REST API. The output directory, the job summary, and the SARIF and Pages files are writes on the runner itself, and a failure there still fails the run. The Report is unchanged.

### Corpus manifest provenance on the Report

The published policy manifests carry a `provenance` block, and the corpus reader used to drop it. The reader now decodes it, and the Report records it as `provenance.intel.corpus_manifest`, next to `corpus_digest`: `policy_id`, `policy_query`, `source_corpus_digest`, `selection_index_digest`, `generator` and `generated_at`. A Report can now say which policy and corpus snapshot produced the records it scanned against.

The field is additive and omitted when the corpus has no block, which includes every bundle-file corpus. It is recorded as the corpus wrote it, never validated, and has no effect on any verdict. A malformed block doesn't make an otherwise good corpus unreadable. It is separate from the per-advisory `provenance` whose `trust_tier` decides whether a record may refute.

### Docs

- The operator guide has a new "When a surface can't be written" section, and the README's Quickstart notes that the PR comment and the Issue are best-effort.
- The README's advisory corpus section describes `corpus_manifest`.

### Library surface

Additions: `report.CorpusManifestProvenance` and the `CorpusManifest` field on `report.IntelProvenance`; `pipeline.ManifestProvenance`; and `StatusError` in `resultsink/github`, which carries the HTTP status of a non-2xx write with the same message text as before.
