# v0.6.0

This release takes EPSS and KEV data out of the scanner, moves the Report to `tegron.report.v3`, and has Java and Kotlin scans take their dependency facts from the repository's own Maven or Gradle. Read [Before you upgrade](#before-you-upgrade) before you move your pin: a state ref this release writes can't be read by v0.5.x, the corpus release route needs a signer you name, Java and Kotlin scans now need the build tool on the runner, and the Report's priority fields changed shape.

The scanner no longer embeds an EPSS/KEV snapshot. Findings are ranked only from a signals file the run is given, and every value carries its own date. On the Action's corpus release route, the release's `bundles.json` is verified with cosign against a signer you name before anything in it is read. For Java and Kotlin, `-build-graph auto` runs the repository's Maven or Gradle and checks the resolved graph against the checkout. A graph that lists everything the build installs can now disqualify an advisory on a package the build never resolves, and a graph that cannot be had fails the run. Corpus advisories whose symbol lists are unvetted no longer ground `not_exploitable` on those symbols' absence. Go ingress recognises chi routers. PR re-analysis no longer inherits a verdict across a changed package.

### Verdicts and analysis

**All ecosystems**

- `not_exploitable` grounded on the absence of an advisory's listed symbols needs a vetted symbol set: `osv-declared`, `curated`, or an untagged record from the built-in table. A `diff-lexed` or `cna-declared` set, an unknown tag, or an untagged corpus record leaves the row `undetermined` with `advisory_symbols_unvetted`, unless a lane refutation grounds it. A record's own `trust_tier` doesn't vouch for its symbols (#162).
- PR re-analysis never inherits a verdict across a changed package. Every copy of a package name is compared, so `lodash` {4.17.10, 4.17.21} → {4.17.4, 4.17.21} is a change. A fresh verdict replaces the baseline's when any package the advisory names changed, not only the selected one. Names are compared under their canonical form (PEP 503 for PyPI, lowercased for NuGet), and a package set that can't be read counts as changed (#155, #164).
- PR re-analysis keeps the fresh row of an advisory the baseline holds no row for, instead of dropping it (#155).
<!-- pending: #168 -->
- On the PR fast path (SBOM unchanged), an advisory with no baseline row is assessed and gets a fresh row instead of none. If that assessment fails, it gets an `undetermined` row and a partiality note naming it. When every advisory already has a row, the fast path still does no checkout (#168).
- Stage-error text in a failed step's evidence redacts bare credentials: `PRIVATE-TOKEN:` headers, npm `_authToken=`, `token=` outside a URL, `.netrc` passwords, and GitHub (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), GitLab (`glpat-`) and npm (`npm_`) tokens (#156).

**Priority (EPSS and KEV)**

- The embedded EPSS/KEV snapshot is gone. Findings are ranked only from a signals file the run is given: `-advisory-signals`, `ASSAY_ADVISORY_SIGNALS`, or the `signals.json` at the root of an `-advisory-corpus` directory. Only `signals_version` 1.x loads, and a malformed file fails the run. Without signals no finding carries a priority, and the run summary says so. Priority stays ranking context; nothing that decides a verdict reads it (#167).
- Each value carries its own stamp: `epss_as_of` for EPSS, `kev_catalog_version` and `kev_date_released` for KEV. There is no longer one snapshot date for the whole Report (#167).
<!-- pending: #174 -->
- An advisory takes signals only from the record under its own id, and never fills a missing value from an alias. A CVE-keyed advisory with no record of its own gets no priority, because a GO, PYSEC, RUSTSEC or GHSA record is a roll-up that can stand for several CVEs. Any other advisory takes a CVE alias's record only when no other advisory in the run names that CVE, and only when all such aliases agree. A refused match leaves the row without a priority rather than guessing. This stops a CVE from picking up a sibling CVE's KEV listing through a shared GO alias. The coverage cost is under [Before you upgrade](#before-you-upgrade) (#174).
<!-- pending: #174 -->
- The run summary's `signals:` line counts how many EPSS values are older than `-advisory-signals-max-age`, as `EPSS: <stale>/<total> (<pct>%) older than <bound>`. It warns when over half are past the bound, as well as when even the newest is (#174).

**Go**

- Go ingress recognises chi routers (`github.com/go-chi/chi` and `/v5`). Handlers registered through `Get`, `Post`, `Handle`, `Method`, `Mount` and the other registrars, on the router or inside `Route`, `Group` and `With`, are `http_route` ingresses with the route pattern as selector. `Use`, `Route`, `Group` and `With` themselves are not. A router is identified by import path only (#157).
<!-- pending: #170 -->
- Go ingress recognises gin routers (`github.com/gin-gonic/gin`). Method registrars, `Any`, `Handle` and `Match` on `*gin.Engine`, `*gin.RouterGroup` and `gin.IRoutes`, including routes on a `Group`, are `http_route` ingresses, and `gin.WrapF` and `gin.WrapH` ingress as the handler they wrap. `c.Param`, `c.Query` and `c.PostForm` carry taint (#170).
<!-- pending: #178 -->
- More gin `*gin.Context` accessors carry taint, the Bind family taints its target, and `NoRoute` and `NoMethod` are ingresses. Selectors on a gin `Group` and a chi `Route` carry the full composed pattern, such as `/v1/users/:id`; a prefix that isn't a constant keeps the local pattern and records a partiality note (#178).
<!-- pending: #178 -->
- Go ingress recognises echo routers (`github.com/labstack/echo/v4`): method registrars on `*echo.Echo` and `*echo.Group`, groups, `echo.Context` accessors and `WrapHandler`. `Use`, `Pre` and echo's own `ServeHTTP` are not ingresses (#178).

**Java and Kotlin**

- Dependency facts (versions, scopes, artifact files) come from a graph the repository's own Maven or Gradle resolved, checked against the checkout before any reader trusts it. The static `pom.xml`, Gradle script, lockfile and catalog readers are removed. A graph that can't be had fails the run with a typed cause, after the Report and every sink are published (#165).
- With the graph off, JVM dependency versions are `undetermined` (`build_graph_absent`), so nothing is disqualified on the version axis (#165).
- Gradle's other runtime classpaths, such as `integrationTestRuntimeClasspath`, must resolve, and a version they hold that differs from `runtimeClasspath`'s keeps the version unresolved. A checkout that holds both a Maven and a Gradle build is never complete on one tool's graph (`other_tool_build`) (#165).
- A cve-watch run whose graph failed holds its cursor, so those advisories are assessed again on the next run (#165).
- A Gradle graph binds the build logic of every included build and `buildSrc`, and a graph file is rejected when any of those files changed (#169).
- When the graph provably lists everything the build installs, an advisory on a Maven package the build doesn't resolve is `disqualified` with `no_manifest_entry`, as the uv and npm lockfile lanes already do. Symbol resolution for such a package reports `dependency_not_in_build`, scoped to that package, in place of a run-wide `tool_failure`. Completeness is withheld for anything the producer doesn't recognise, including unknown Maven plugins, script task actions, checked-in archives and build files no module reads (#171).
- A repository module's file under a build directory, such as a `file:` or `mavenLocal()` repository kept in `build/`, withholds completeness unless the graph lists it (#183).
- Dependency reachability roots an overridable method only when the JDK can name it by signature, using a table of `java.base`'s 1,100 types from Temurin 21. The table applies only when the stated JDK is 21 and every module's toolchain is known to match; otherwise every method stays a root, as before (#172).
- A JAR's own copy of a `java/` class is never walked as dependency code, since the JVM loads only the JDK's, and `SignedObject.getObject` and `SealedObject.getObject` are reflection hazards (#172).
- Copies of classes in other packages the JDK defines, such as xml-apis' `javax/xml/parsers`, are left out too, read from a table of Temurin 8, 11 and 16 through 27. On an unrecorded or newer JDK, a package the JDK could add is treated the same way (#181).

**JavaScript**

- In a stock Create React App, a relative import of an in-tree `.css`, `.scss`, `.sass` or `.less` file no longer raises a run-wide `unresolved_module`. It leaves one scoped limit on `css-loader`, `mini-css-extract-plugin`, `style-loader` and `webpack`. Any other toolchain, or a CRA project with added tooling, keeps the run-wide limit (#150).
- Dynamic-loading flags are more precise: `require` declared as a parameter or tested rather than called, and `Function` built only from plain literals that run no code, no longer flag. The global object is now tracked through `globalThis`, `global`, `window`, `self` and their aliases, so `g.eval(s)` or `globalThis[k](s)` flags `evaluated_code`, as does any other reference to `Function` (#152).

### Report format

This release changes the Report's schema. A consumer that gates on `schema_version` sees `tegron.report.v3`.

- `schema_version` is `tegron.report.v3`. Reading a v2 or v1 Report upgrades it to v3, dropping a priority block that has no per-value stamp (#173).
- `priority.snapshot` is removed. Each value carries its own stamp: `epss_as_of`, `kev_catalog_version` and `kev_date_released`. `kev_listed` appears only when `true` (#167).
- `epss_score` is written whenever the finding has an EPSS value, a score of 0 included, and `epss_percentile` whenever the signals file sourced one, 0 included (#173).
- New optional fields: `provenance.intel.signals_digest`, naming the signals file the findings were ranked with (#167); `provenance.intel.corpus_signer` (`identity`, `issuer`), set only when a corpus release signature was verified (#163); and `build_graph` on every Java and Kotlin scan, with `source` (`build_tool`, `build_tool_file` or `off`) and, when the graph could not be had, `cause` (`kind`, `detail`) (#165).
- New `undetermined_reason` value: `advisory_symbols_unvetted` (#162).
- New partiality reasons from the Java and Kotlin lanes: `tool_failure:build_graph_absent` and `other_tool_build` (#165), `unlisted_install` and `dependency_not_in_build` (#171).

### CLI

- `-advisory-signals` (env `ASSAY_ADVISORY_SIGNALS`) takes the EPSS/KEV signals file, `signals.json` or `signals.json.gz`. Without it the run uses the `signals.json` of an `-advisory-corpus` directory, when there is one. `-advisory-signals-max-age` (default 7 days) sets when the run summary warns that the file is stale; a stale file still loads (#167).
- `-build-graph auto|<file>|off` (default `auto`) sets where a Java or Kotlin scan's dependency graph comes from: the repository's own Maven or Gradle, a graph written ahead of time by `resolve-graph`, or none. `-build-graph-tool auto|maven|gradle` (env `ASSAY_BUILD_GRAPH_TOOL`) picks the tool; `auto` fails when both builds sit at the repository root (#165).
- `-subject-java-version` and `-subject-maven-profiles` are now the graph's run conditions. Under `auto`, a build tool on another JDK major fails `jdk_mismatch`, profiles go to Maven as `-P`, and stating profiles for a Gradle build fails. A graph file must record the same statement (#165).
- The stated Java version is the JDK the program runs on, and must share the build JVM's major (#172).
- `resolve-graph` writes `assay.buildgraph/v2` and takes only `-tool`, `-profiles` and `-java-version`, besides `-dir` and `-out`; `-D` and `-env` are removed (#165).
- `resolve-graph` refuses to write a graph that includes a Gradle build outside the checkout (#169).
<!-- pending: #168 -->
- The `pr-inherit` summary prints an `assessed:` line naming the advisories the fast path assessed because the baseline held no row for them (#168).

### Action

- The corpus release route verifies the release's `bundles.json` with cosign (v3.1.3, pinned by sha256) against `bundles.json.sigstore.json` before it reads anything in it. The signer is the one you name in the new `corpus-signer-identity` and `corpus-signer-issuer` inputs, which have no default; Assay doesn't choose whose signature you trust. A missing input or signature, or a failed check, fails the run. The route also needs `github.com` and `tuf-repo-cdn.sigstore.dev` (#163).
<!-- pending: #177 -->
- The corpus release route also downloads the release's `signals.json.gz`, after the signature check, checks it against the sha256 the signed `bundles.json` names, and passes it to the scanner as `-advisory-signals`. A release that can't supply verified signals fails the run. With an `advisory-corpus` directory the Action passes nothing, and the directory's own `signals.json` applies (#177).
- On a branch ref such as `@main`, the Action's default `scanner-version` alias moved from `v0.4` to `v0.5`. A tag always runs the scanner release it names (#158).

- The README and operator guide use a floating minor-version pin in place of the old v0.2.0 SHA examples, and document `resolve-graph`, the subject Java and Maven flags and the observed-Go trust variables. The threat model names `resolve-graph` as a command that runs repository code. `CHANGELOG.md` points to `docs/releases/` (#160).

### Before you upgrade

**Move your Action pin.** Workflows pinned to `@v0.5` keep fetching that release. To get this one, use `uses: ferralon-ai/ferralon-assay@v0.6` (or `@v0.6.0`, or that tag's commit SHA). If you set `scanner-sha256`, update it to the v0.6.0 tarball's checksum. Leave `scanner-version` unset and the tag runs the v0.6.0 scanner.

**Pinning back to v0.5.x is a one-way door.** The Report schema is now `tegron.report.v3`, and v0.5.x can't read a state ref (`refs/assay/state`, or the `state-ref` you configured) written by v0.6. If a repository runs a v0.6 baseline and then pins back to `@v0.5`, every run fails on state read until the state ref is deleted, for example with `git push origin --delete refs/assay/state` (#173).

**The corpus release route needs a signer you name.** If you set `advisory-corpus-policy` with `advisory-corpus-repo`, and `advisory-corpus-ref` names a corpus release (the default `main` resolves to the latest one), set `corpus-signer-identity` and `corpus-signer-issuer` from the corpus's own consumer documentation. Without them the run fails. The runner must reach `github.com` and `tuf-repo-cdn.sigstore.dev` (#163).

<!-- pending: #177 -->
**The corpus release must ship signals.** On the same route, the Action needs the corpus release to publish a signed `signals.json.gz`: its `bundles.json` must be `bundle_version` 1.1.0 or later and carry a `signals` object naming the file's sha256. A release without them fails the run, including a release read for a manifest-only policy (#177).

**Expect fewer findings to carry a priority.** The scanner no longer ships EPSS or KEV data. A run that is given no signals file reports no priority on any finding. That includes a run with no corpus, and the Action's git fetch of a corpus, which doesn't fetch its `signals.json` (#167).

<!-- pending: #174 -->
**The coverage cost of the signals join.** CVE-keyed rows no longer take priority from an alias's roll-up record (PYSEC, GO or RUSTSEC). Measured on `ferralon-ai/vulnerability-corpus` at `7a79df2` (148,387 advisories, 127,147 signals records), 3,924 CVE-keyed and 3,781 GHSA-keyed advisories that a join through aliases would rank now carry no priority. Nearly all of them have only a PYSEC, GO or RUSTSEC roll-up record, and 12 have a KEV-listed alias record. Another 19 GHSA advisories get none because their CVE aliases' records disagree. This is honest absence, not a guess: the corpus would need to publish CVE-keyed records for the CVEs a roll-up covers. On that same file, 98% of EPSS values were more than 7 days old when measured on 2026-10-20, so expect the run summary's staleness warning (#174).

**Java and Kotlin scans run your build tool.** Under the default `-build-graph auto`, which is what the Action runs, the scan resolves dependencies with the repository's `./mvnw` or `./gradlew`, or `mvn` or `gradle` on `PATH`, using the job's environment and JDK. That runs the build's scripts and plugins, and the tool fetches from the repositories the build configures. The runner needs the tool, the JDK your build uses, and credentials for private repositories. A scan that can't resolve the graph publishes the Report and then fails the job, with the cause in `build_graph.cause`. On the CLI, `-build-graph off` scans without a graph and leaves JVM versions `undetermined` (#165).

**Regenerate saved build graphs.** A graph written by v0.5.x's `resolve-graph` is rejected as `graph_rejected:schema`. Write it again with this release's `resolve-graph`, and pass `-java-version` and `-profiles` matching what the scan states (#165).

**Expect some rows to change verdict.** Rows whose `not_exploitable` rested on the absence of an unvetted symbol list become `undetermined` (`advisory_symbols_unvetted`) (#162). Java and Kotlin advisories on packages a complete build graph doesn't install become `disqualified` (`no_manifest_entry`) (#171). The changes behind this are listed under "Verdicts and analysis".

**Parsing the Report?** It is not additive this time; see "Report format" (#167, #173).

### Breaking (library API)

This affects Go code that imports Assay as a module, and analyzer plugins built outside this repository.

- `report.Priority` drops `Snapshot`, and `KEVListed` is omitted from JSON when false. Trigger runs no longer rank findings by themselves: a request ranks only with the `Signals` it is given, and a nil `Signals` reports no priority. `Signals` is typed from an internal package, so callers outside this module can pass only `nil` (#167).
<!-- pending: #175 -->
- The public `signals` package lifts that limit: a value from `signals.Load` or `signals.Parse` is exactly the type the `Signals` field takes (#175).
- `report.SchemaVersion` is `tegron.report.v3`. `Upgrade` takes a v2 Report to v3 and drops a priority without per-value stamps (#173).
- `pipeline.WithSubjectJavaVersion`, `pipeline.WithSubjectMavenProfiles` and `AssessConfig`'s `SubjectJavaVersion` and `SubjectMavenProfiles` are removed, and the `java.version` and `maven.profiles` target-environment entries are no longer sent to plugins. State the Java version and profiles as the build graph's conditions instead (#165).
- `buildgraph.Schema` is `assay.buildgraph/v2`. `buildgraph.Load` rejects a v1 graph (#165).
- The Kotlin plugin's capability manifest is 1.2.0. Its resolvers are `gradle` and `maven`, and the `gradle_version_resolution` boundary is gone (#165).
