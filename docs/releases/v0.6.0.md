# v0.6.0

This release has Java and Kotlin scans take their dependency facts from the repository's own Maven or Gradle, lets JavaScript scans read and follow calls into lock-pinned, integrity-verified dependency code, and makes EPSS and KEV priority a verified input with a date on every value. It also moves the Report to `tegron.report.v3`. Read [Before you upgrade](#before-you-upgrade) before you move your pin: a state ref this release writes can't be read by v0.5.x, Java and Kotlin scans now run the build tool on the runner, the corpus release route needs a signer you name, and the Report's priority fields changed shape.

For Java and Kotlin, `-build-graph auto` runs the repository's Maven or Gradle and checks the resolved graph against the checkout, so a complete graph can disqualify an advisory on a package the build never resolves. Reachability follows lambdas, string concatenation and value calls, treats classes the JDK defines as the JDK's own, and leaves out dependency classes that cannot link. JavaScript scans now read dependency code by default: each lock-pinned npm, pnpm or yarn classic package is fetched or read from a cache, verified against the lock's integrity hash, and call paths are traced through it to the advisory's symbols. The JavaScript call graph also lists the call sites it declined, so a consumer can tell where it is incomplete. Version resolution for JavaScript and Python reads the build's script surfaces and accepts more of the install forms real projects use. The scanner no longer embeds an EPSS/KEV snapshot: findings are ranked from a signals file the run is given, whose digest the scanner verifies, and the Action's corpus release route verifies the release's signature against a signer you name. Go ingress recognises chi routers and the Go version axis reads `go.mod` replace directives, and the .NET lane can disqualify an advisory on a NuGet package a closed build doesn't contain. A new `library-entrypoints` input states which of your packages code outside the build may import, so a Go refutation rests on what you declare, and Go reflection, cgo and build-constraint bounds are decided per advisory. OpenVEX statements for reachability refutations carry the `vulnerable_code_not_in_execute_path` justification. A public `signals` package lets Go callers outside this module load a signals file.

### Verdicts and analysis

**All ecosystems**

- `not_exploitable` grounded on the absence of an advisory's listed symbols needs a vetted symbol set: `osv-declared`, `curated`, or an untagged record from the built-in table. A `diff-lexed` or `cna-declared` set, an unknown tag, or an untagged corpus record leaves the row `undetermined` with `advisory_symbols_unvetted`, unless a lane refutation grounds it. A record's own `trust_tier` doesn't vouch for its symbols (#162).
- PR re-analysis never inherits a verdict across a changed package. Every copy of a package name is compared, so `lodash` {4.17.10, 4.17.21} → {4.17.4, 4.17.21} is a change. A fresh verdict replaces the baseline's when any package the advisory names changed, not only the selected one. Names are compared under their canonical form (PEP 503 for PyPI, lowercased for NuGet), and a package set that can't be read counts as changed (#155, #164).
- PR re-analysis keeps the fresh row of an advisory the baseline holds no row for, instead of dropping it (#155).
<!-- pending: #168 -->
- On the PR fast path (SBOM unchanged), an advisory with no baseline row is assessed and gets a fresh row instead of none. If that assessment fails, it gets an `undetermined` row and a partiality note naming it. When every advisory already has a row, the fast path still does no checkout (#168).
- Stage-error text in a failed step's evidence redacts bare credentials: `PRIVATE-TOKEN:` headers, npm `_authToken=`, `token=` outside a URL, `.netrc` passwords, and GitHub (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), GitLab (`glpat-`) and npm (`npm_`) tokens (#156).

**EPSS and KEV priority**

Priority is ranking context. Nothing that decides a verdict reads it.

- The embedded EPSS/KEV snapshot is gone. Findings are ranked only from a signals file the run is given: `-advisory-signals`, `ASSAY_ADVISORY_SIGNALS`, or the `signals.json` at the root of an `-advisory-corpus` directory. Only `signals_version` 1.x loads, and a malformed file fails the run. Without signals no finding carries a priority, and the run summary says so (#167).
- Each value carries its own stamp: `epss_as_of` for EPSS, `kev_catalog_version` and `kev_date_released` for KEV, in place of one snapshot date for the whole Report (#167).
- The scanner recomputes `signals_digest` from the file's `signals_version`, `record_count` and `records`, and refuses the file when it differs from the stated value; the run fails with an error naming both digests. A file with a repeated key, or two keys that differ only in case such as `Score` and `score`, is refused too. `provenance.intel.signals_digest` is the digest the scan verified, on every route that loads signals (#188).
- An advisory takes signals only from the record under its own id, and never fills a missing value from an alias. A CVE-keyed advisory with no record of its own gets no priority, because a GO, PYSEC, RUSTSEC or GHSA record is a roll-up that can stand for several CVEs. Any other advisory takes its CVE aliases' records only when they all agree, and never one that another advisory in the run names. A refused match leaves the row without a priority. This stops a CVE from picking up a sibling CVE's KEV listing through a shared GO alias (#174).
- The run summary's `signals:` line counts the EPSS values older than `-advisory-signals-max-age`, as `EPSS: <stale>/<total> (<pct>%) older than <bound>`. It warns when over half are past the bound, as well as when even the newest is (#174).

**Go**

- Go ingress recognises chi routers (`github.com/go-chi/chi` and `/v5`). Handlers registered through `Get`, `Post`, `Handle`, `Method`, `Mount` and the other registrars, on the router or inside `Route`, `Group` and `With`, are `http_route` ingresses with the route pattern as selector. `Use`, `Route`, `Group` and `With` themselves are not. A router is identified by import path only (#157).
<!-- pending: #170 -->
- Go ingress recognises gin routers (`github.com/gin-gonic/gin`). Method registrars, `Any`, `Handle` and `Match` on `*gin.Engine`, `*gin.RouterGroup` and `gin.IRoutes`, including routes on a `Group`, are `http_route` ingresses, and `gin.WrapF` and `gin.WrapH` ingress as the handler they wrap. `c.Param`, `c.Query` and `c.PostForm` carry taint (#170).
<!-- pending: #178 -->
- More gin `*gin.Context` accessors carry taint, the Bind family taints its target, and `NoRoute` and `NoMethod` are ingresses. Selectors on a gin `Group` and a chi `Route` carry the full composed pattern, such as `/v1/users/:id`; a prefix that isn't a constant keeps the local pattern (#178).
<!-- pending: #178 -->
- Go ingress recognises echo routers (`github.com/labstack/echo/v4`): method registrars on `*echo.Echo` and `*echo.Group`, groups, `echo.Context` accessors and `WrapHandler`. `Use`, `Pre` and echo's own `ServeHTTP` are not ingresses (#178).
<!-- pending: #234 -->
- Taint follows a value through calls into the standard library and dependencies, so `r.Header.Get`, `r.URL.Query().Get`, `r.FormValue` and `chi.URLParam` results are tainted, and the modelled sanitizers such as `strconv.Atoi` clear it. A tainted value stored in a struct field taints the struct, and type assertions and map or string lookups carry taint. More Go findings are graded `attacker_tainted`, and the credited entry point can differ from v0.5: a change, not a break. When several handlers reach one sink, the credited entry point is the same on every run, and a taint finding's trace shows the call chain the call graph has rather than a direct handler-to-sink call. Taint picks the attacker-tainted trace, entry point and grade; no verdict reads it (#234).
- The Go version axis reads `replace` directives in `go.mod`. A same-module version replace gives the version the build compiles, so a module required at one version and replaced with another is judged on the replacement. A fork or local-directory replace leaves the module with no version and discloses `source_unpinned`, so nothing is `disqualified` on the version axis for it. The SBOM, the verdict and the OpenVEX statement agree on the version (#201).
- A run that evaluates many advisories runs govulncheck, builds the Go call graph and symbol index, and finds taint ingresses once per build, not once per advisory. Verdicts are unchanged (#205, #206).
- `library-entrypoints` (`auto`, `none`, or a list of paths relative to the repository root with `!path` exclusions) states which of your packages code outside the build may import. A Go refutation is withheld when an importable package reaches the refuted module. `auto` infers those packages and no longer counts packages under `cmd`, `example(s)`, `test(s)` and `testdata`; `none` says the build ships programs only; a list replaces the inference. A declaration that matches no package withholds. A load that does not type-check withholds unless the declaration takes packages out of `auto`'s set. A `not_exploitable` that stands only because of a declaration carries it as `evidence.assumptions`, and the Report records the set each lane used as `library_entrypoints` (#264).
- Reflection is bounded per advisory. The scanner computes what calls made through `reflect` and a template's `Execute` can reach over the whole program, including functions used as values, methods of types converted to interfaces and `runtime.SetFinalizer` finalizers. A Go refutation is withheld as `reflection:call` only when that reach holds one of the advisory's vulnerable symbols, when it cannot be computed (a package that does not type-check), or when the refuted package is not in a Go module. A module that merely reaches `reflect` no longer withholds every refutation, and a call graph declares the same reasons (#258, #260, #269).
- The left-out-files check counts a file excluded by platform or build tag when its own package reaches the module, whatever it imports. A file excluded only by `goN.M` release tags drops out of the check only when the subject's Go release is established from the toolchain the request names; otherwise it counts. The standard library's own excluded files are checked too. A package is the standard library's only when `go list` marks it standard, so a dotless replace module is followed as a module, and an advisory with no OSV entry for the module counts every package of it (#261, #262, #267, #271).
- A two-part `go` line such as `go 1.21` is not a toolchain minimum. Only a `toolchain` line, or a three-part `go` line at 1.21.0 or later, bounds the toolchain; otherwise the build's toolchain is probed, or the fact is unresolved. A toolchain resolved by the analyzer's own `go` command is never requested as the subject's (#266).
- The scanner loads the cgo variant the `go` command resolves for the build, from `CGO_ENABLED` and `CC` as the environment sets them. When it cannot resolve one, a refutation is withheld as `cgo:env_unresolved`. The standard library's own cgo holds no cgo limit, and a scoped limit counts against a standard-library advisory only when it names the standard library, so a dependency's cgo no longer withholds every standard-library refutation (#253, #256).

**Java and Kotlin**

- Dependency facts (versions, scopes, artifact files) come from a graph the repository's own Maven or Gradle resolved, checked against the checkout before any reader trusts it. The static `pom.xml`, Gradle script, lockfile and catalog readers are removed. A graph that can't be had fails the run with a typed cause, after the Report and every sink are published (#165).
- With the graph off, JVM dependency versions are `undetermined` (`build_graph_absent`), so nothing is disqualified on the version axis (#165).
- Gradle's other runtime classpaths, such as `integrationTestRuntimeClasspath`, must resolve, and a version they hold that differs from `runtimeClasspath`'s keeps the version unresolved. A checkout that holds both a Maven and a Gradle build is never complete on one tool's graph (`other_tool_build`) (#165).
- A cve-watch run whose graph failed holds its cursor, so those advisories are assessed again on the next run (#165).
- A Gradle graph binds the build logic of every included build and `buildSrc`, and a graph file is rejected when any of those files changed (#169).
- When the graph provably lists everything the build installs, an advisory on a Maven package the build doesn't resolve is `disqualified` with `no_manifest_entry`. Symbol resolution for such a package reports `dependency_not_in_build`, scoped to that package, in place of a run-wide `tool_failure`. Completeness is withheld for anything the producer doesn't recognise, including unknown Maven plugins, script task actions, checked-in archives and build files no module reads (#171).
- A repository module's file under a build directory, such as a `file:` or `mavenLocal()` repository kept in `build/`, withholds completeness unless the graph lists it. The roots of the file repositories a build declares (`mavenLocal()`, a `file:` URL, `flatDir`, and settings and `pluginManagement` repositories) count as outside the build, and an Ivy repository with no URL withholds completeness (#183).
- The Gradle producer reads each project's description, repositories and tasks once the task graph is ready, so a build script that sets its Java toolchain after a `tasks.all {}` resolves under `-build-graph auto` instead of failing (#183).
- A Gradle task whose configuration fails while the graph is resolved withholds completeness, with the failure as the reason (#185).
- Reachability follows a lambda or method reference to the method it implements, and a string concatenation to each object operand's `toString`. Calls on arrays, and listed methods of `String`, `StringBuilder`, `StringBuffer` and the boxed primitives that read only their receiver and value arguments, are leaves. A search that used to stop at these calls can now end empty (#100).
- A call whose receiver no loaded class or lambda can implement, such as a `Proxy`, a CGLIB or ByteBuddy subclass, a Spring Data repository or a Feign client, keeps the search open (#100).
- Dependency reachability roots an overridable method only when the JDK can name it by signature, using a table of `java.base`'s 1,100 types from Temurin 21. The table applies only when the stated JDK is 21 and every module's toolchain is known to match; otherwise every method stays a root (#172).
- A JAR's own copy of a `java/` class is never walked as dependency code, since the JVM loads only the JDK's, and `SignedObject.getObject` and `SealedObject.getObject` are reflection hazards (#172).
- Copies of classes in other packages the JDK defines, such as xml-apis' `javax/xml/parsers`, are left out too, read from a table of Temurin 8, 11 and 16 through 27. On an unrecorded or newer JDK, a package the JDK could add is treated the same way (#181).
- A loaded class whose only path to a loaded interface runs through an unopened dependency type is no longer left out of that interface's dispatch, and a loaded default method beside an unopened dependency interface no longer settles the call, since that interface may override it. Such rows are `undetermined` (`unloaded_dependency`) or `reachable_candidate` where they were `not_exploitable` (#186).
- Java dependency reachability roots no class that cannot link. A dependency class with a supertype that is on no classpath and not the JDK's, such as one implementing an interface from an optional dependency the build never resolves, contributes no roots, and a lambda implementing such an interface is not rooted. This holds when the graph lists every install, every runtime JAR was read, the run records a JDK later than 8, the first-party class output covers the sources and the program launches from a named entry; a WAR or container deployment, an unlisted classpath and every Kotlin scan keep their roots (#187).
- On a linked run, a loaded class that cannot link, and a lambda whose functional interface is on no classpath and not in a JDK package, are no longer possible receivers of every virtual and interface call, so rows that were `undetermined` (`unloaded_dependency`) can resolve. The conditions are #187's, so Kotlin scans are unchanged. Linkage assumes the runtime JDK's standard platform packages: a JDK vendor's own packages, such as OpenJ9's `com/ibm` and JavaFX, are not among them, and a javaagent can append to the system class path (#196).
- A call whose receivers include a loaded override that reaches the sink, and a class that inherits a higher-order body such as `forEach` from a JDK class off the classpath, reports `reachable_candidate` where it reported `undetermined`. The hazard is still raised, so that call can't end in `not_exploitable` (#193).
- A multi-release JAR member that only a `java/` ancestor could declare no longer withholds linkage as `multi_release_unmerged`. This admits a method whose descriptor names a type no JDK release defines, such as the synthetic accessor in snakeyaml 2.2's `META-INF/versions/9` `Logger$Level`, and any field. Ancestors outside `java/`, classpath ancestors and methods whose descriptors name only JDK types still withhold it (#197).
- When the build's Maven local repository sits inside the checkout (for example `-Dmaven.repo.local=.m2/repository`), the launch-option scan leaves out the artifact files Maven resolved there, as it does for a repository in `~/.m2`. Third-party POMs cached in the checkout no longer withhold a search as `launch_jvm_option`. Without a Maven graph that names the repository, nothing is left out (#235).

**JavaScript and Python**

- Version resolution reads the script surfaces of a build: Dockerfiles, shell scripts, Makefiles, CI configs and `package.json` scripts. An install command outside the allowed forms, or one that doesn't bind to a file read here, withholds every version in the build, so no advisory is `disqualified` on the version axis. A script that sources a file outside the read surfaces withholds every version (#137).
- The Python allowed install forms are `uv sync --locked` and `--frozen`, `poetry install`, `pdm sync`, `pipenv install --deploy`, `pipenv sync` and `pip install -r <file>` (#137).
- `no_manifest_entry` disqualifies a package missing from every read manifest only when no script surface withheld anything and every requirements file with requirements is hash-checked or installed only with `--no-deps`. An unhashed requirements file installed with its dependencies, or installed by nothing read here, such as a `requirements.txt` beside a `uv.lock`, leaves the package open (#137).
- A script that sources a file outside the read set no longer withholds every version when the file only sets `PATH`. A literal `<dir>/bin/activate` passes when the command just before it, in the same shell, always runs and created that venv with `python -m venv`, `virtualenv` or `uv venv`; so do `$NVM_DIR/nvm.sh`, `~/.nvm/nvm.sh` and `~/.cargo/env` (also under `$HOME`). A guarded or conditional creation and any other sourced file still withhold. A GitHub step, or a GitLab job's `before_script` and `script` in a plain single-document file, count as one shell (#198).
- Git's sample hooks (`.git/hooks/*.sample`, and a submodule's under `.git/modules/`) no longer count as install surfaces, unless something in the build may reach them: a surface that mentions `.git`, `hooks`, `.sample` or `dotglob`, a dot-glob such as `.g*`, a `cd` or `--prefix` to an expanded directory, another in-tree file that names them, or a symlink into `.git`. Then they are classified as before (#212).
- A Procfile or other data value that starts with a redirect, such as `web: >/dev/null <command>`, is read as a command instead of being skipped; only a YAML block-scalar header is skipped (#225).
- A `pyproject.toml` `[dependency-groups]` table, the `[tool.poetry]` dependency tables (main, dev and group) and the uv and pdm dev-dependencies are read as declarations. An exact pin resolves and a range fails open. A range is covered only by a same-directory lock of the tool that installs the table: `uv.lock`, `pdm.lock` or `poetry.lock` for groups, and the tool's own lock for a `[tool.*]` table. A table that cannot be read withholds: a malformed group or `include-group`, a local-file entry, or a Poetry constraint that does not translate. A requirement written `name(spec)` is keyed on its name (#250).
- A script line `pip install -U pip` (or `python -m pip install --upgrade pip`) withholds only the `pip` coordinate. A pip config named in a script surface or GitLab include, `PIP_CONFIG_FILE`, a `pip.conf` or `pip.ini` in the tree, or an index or find-links flag on the line withholds every pin around it (#254).

**JavaScript**

- **Dependency code.** With `-dependency-code=fetch` or `offline`, a scan reads each lock-pinned npm package, verifies it against the lock's integrity hash, follows calls from first-party code into it, and resolves an advisory's symbols on the copy the build loads. `fetch` downloads each tarball by name and version from the registry the project configures; `offline` reads only a pre-seeded `-dependency-cache` and opens no socket. `fetch` is the default; `off` reads no dependency code (#210, #217, #257).
- Each package copy is kept apart (`npm:qs@6.7.0#parse`) and placed by Node's own resolution, nested before hoisted, so only a copy reached from first-party code resolves. When installed copies disagree, an on-path copy at any version the advisory's ranges don't exclude can resolve. An unread package, a native addon, or a package past the per-run source cap keeps a limit scoped to that package; an install script, an unread package whose lock doesn't record install scripts (npm v1, pnpm, yarn classic), a `binding.gyp`, a computed load inside dependency code or a budget overrun keeps the limit run-wide (#217).
- Credentials for `fetch` come only from the project `.npmrc`, `NPM_CONFIG_USERCONFIG` and `NPM_CONFIG_REGISTRY`. A token is presented only to the host it names, `${VAR}` references read only `NODE_AUTH_TOKEN`, `NPM_TOKEN` and the names you add with `-dependency-npmrc-env`, and a malformed config fetches nothing. `$HOME/.npmrc` and the global npmrc are never read, and no token appears in an artifact, log or error (#210).
- pnpm (`lockfileVersion` 5.4, 6.0 and 9.0) and yarn classic locks are placed as well. A load inside one is answered from the lock's own edges; a load the lock doesn't declare may find any copy pnpm or yarn could have hoisted, and resolves only when that is one copy. Workspace patterns are read when they are literal paths or one trailing `/*`. pnpm patches, `overrides` that match the lock, and yarn `resolutions` a range check decides are modelled; pnpmfiles, unmodelled settings and any other shape leave the layout incomplete (#220).
- pnpm workspaces with a comment block before a single `---`, an `allowBuilds` map, `blockExoticSubdeps: true|false`, or `.` in `packages` are now read (#227).
- The dependency layout honours the install-surface veto: when the build may install something no lock read here records, the call graph keeps its edges and withholds run-wide with `uninspectable_package` (#223).
- A pnpm region is read only when pnpm itself would take every importer as up to date with its manifest: the same specifiers, field by field, the same `dependenciesMeta` and `publishDirectory`, and locked versions inside their ranges. Otherwise it withholds run-wide (#228).
- The JavaScript lane withholds when an `.npmrc` names pnpm's global virtual store or spells a key through `${...}` or an escape, and a script surface that sets `PNPM_CONFIG_*` withholds like any other installer variable it doesn't keep (#229). Every `.npmrc` key is read the way npm's `ini` package and pnpm read it, so a quoted, `[]`-suffixed, camel-cased or BOM-prefixed spelling of `virtual-store-dir`, `modules-dir` or `pnpmfile` is seen; a key that can't be read that way withholds (#230).
- `require('.')`, `require('..')`, `import '..'` and `import('..')` resolve as directories, as Node resolves them, to the package.json `main` or `index`. A directory load the lane can't decide declares `unresolved_module` (#222).
- More install forms are allowed. `npm ci` takes `--production` and `--omit`, `--include` or `--only` with a value, and `npm` scripts may set `NPM_CONFIG_PRODUCTION`, `OMIT`, `INCLUDE` or `ONLY` (either case) ahead of the command or in the environment; any other npm configuration variable still withholds (#213, #214). `npm start`, `npm run` and `npm run-script` take one literal `--prefix <dir>`, and `concurrently "<cmd>" ...` is read command by command (#214). A bare `npm install` (or `npm i`) is allowed outside a workspace when the lock covers its project and no `.npmrc` it reads changes how the lock is used (#215). `pnpm install --frozen-lockfile` stays allowed, with only `--production` and `--ignore-scripts` beside it (#213). No yarn install is allowed, `--frozen-lockfile` included, because yarn 1 can install outside the lock in a workspace under that flag (#224).
- A v1 package-lock covers its root project when the version it records for every direct dependency and peer satisfies the declared range (#215). For v2/v3 locks, a root or workspace `peerDependencies` range must equal the spec the lock recorded (#216), and the locked copy must satisfy it (#219). The range matcher models npm's usual forms, including `||`, x-ranges, partials and hyphen ranges, and anything else counts as not satisfied (#219).
- The call graph lists the call sites it declined (`Unresolved`), each with its caller, callee as written, arity and reason, and the candidate targets when that set is provably complete. It also lists the first-party functions whose value can reach an untracked call (`Escaped`). A site that can't be listed declares `relationship_unexpressed:unlisted_sites`, as does every graph that already declares `evaluated_code`. Edges, roots and other partiality are unchanged (#208). A scan that reads dependency code and loads an npm package from first-party code also declares `unlisted_sites`, because that load is itself a declined site, so `Unresolved` doesn't bound it; its completeness is unchanged, since that load already made it partial (#208).
- With dependency code read, `unlisted_sites` is declared only when dependency code contributes a limit, a first-party site is declined, or a run-wide uninspectable limit applies. Reading dependency code alone no longer declares it (#236).
- A first-party load of a package whose code was read, verified and unpatched no longer declares a run-wide `uninspectable_package`. The load is linked to every file any resolver may select (Node, a bundler, the `browser` field and the package's `exports`, `main`, `module` and nested `package.json` files), and the decline is dropped only when all of them were parsed and their edges landed in the graph. A call through such a load is re-resolved against the read code. Loads of unplaced, unread, patched or self-referencing packages keep the decline. A package that is unread, patched or compiled keeps a scoped limit that applies to every advisory (#255).
- Lock readers read YAML scalars through a closed grammar: a pnpm, yarn classic or yarn berry lock that holds a quoted escape, a doubled single quote, text after a closing quote or another shape the readers cannot decode is withheld whole (#231). A pnpm layout a non-frozen install would re-resolve is withheld: `pnpm.overrides`, `patchedDependencies` and `ignoredOptionalDependencies` in `package.json`, a `file:` tarball whose bytes no longer match the lock's integrity, a `file:` directory whose dependencies no longer match the lock's snapshot, and a workspace member that shares a registry dependency's name and locked version (#232).
- npm ranges and versions are read as node-semver reads them: text splits on ASCII whitespace only, and leading zeros, malformed prerelease or build identifiers, numeric parts beyond 2^53-1 and `=`-prefixed bounds read as plain versions are rejected. A range that is rejected fails open, so the version is not disqualified on it (#268).
- In a stock Create React App, a relative import of an in-tree `.css`, `.scss`, `.sass` or `.less` file no longer raises a run-wide `unresolved_module`. It leaves one scoped limit on `css-loader`, `mini-css-extract-plugin`, `style-loader` and `webpack`. Any other toolchain, or a CRA project with added tooling, keeps the run-wide limit (#150).
- Dynamic-loading flags are more precise: `require` declared as a parameter or tested rather than called, and `Function` built only from plain literals that run no code, no longer flag. The global object is now tracked through `globalThis`, `global`, `window`, `self` and their aliases, so `g.eval(s)` or `globalThis[k](s)` flags `evaluated_code` (#152).
- `require`, `createRequire` results, `module`, `process`, `Function`, `eval`, `_load` and `dlopen` are accepted only in forms the lane fully recognises. Any other use declares the limit the lane already uses for computed or out-of-tree loads (`computed_require_specifier`, `unresolved_module`, `evaluated_code`) (#190).
- `x instanceof Function`, and `Function.prototype` read at once for `apply`, `call`, `bind`, `toString` or `[Symbol.hasInstance]`, no longer flag `evaluated_code`. Every other reference to `Function` still flags (#194).
- Code inside template substitutions (`${…}`), after a regex that holds a quote, and next to an apostrophe in JSX text is read as code instead of being blanked, so a `require`, `eval` or dynamic import there sets its flag and builds its edges. A tagged template keeps its tag's name, so `` require`x` `` and `` Function`x` `` are seen (#195).
- String and template literals are decoded the way the engine reads them: `\xHH`, `\uHHHH`, `\u{…}`, legacy octal escapes and line continuations. A key or specifier written with escapes, such as `'\x63onstructor'`, reads as its value. A `\u` escape in a name outside a literal, such as `eval(...)`, declares `evaluated_code` (#199).
- A run of unclosed `\u{` escapes no longer makes the identifier-escape check quadratic. Results are unchanged (#202).
- The call graph roots any first-party function that opaque code can call back: class members, functions whose name is used as a value, exported functions and named function expressions, and every function in a module that reaches functions by computed name. A sink reached only from such a root is control-flow reachable, never attacker tainted. `require('./plugins/' + n)` and `` import(`./plugins/${n}`) `` get an edge to every in-tree module the prefix can name, and keep their run-wide limit. A literal `import('pkg')` is an ordinary package load and no longer also flags `dynamic_import_specifier`, unless its exports or imports map uses a condition outside Node's defaults or the installed package.json can't be read (#106).
- A bare specifier that names a workspace member is followed as in-tree only when Node's `node_modules` walk finds no other copy. A real `node_modules/foo` or `foo.js` beside member `packages/foo`, or a walk that can't be stat'ed, keeps the run-wide `uninspectable_package` limit (#200).
- A computed read whose key may be `"constructor"` and whose value is called or handed on (`g[k](...)`) is judged by its key, receiver and use, and flags `evaluated_code` unless all three are safe. Literal keys, number keys and keys enumerated from the same receiver's own keys are safe, and `typeof`, comparisons and other read-only uses never flag. A parameter, `this`, an import, a member or a top-level `var` receiver that is called or escapes withholds, as does an ES-module webpack bundle (#203).

**.NET**

- When every project is settled on restore's own `project.assets.json` and nothing else in the tree can bring a package in, an advisory on a NuGet package the build doesn't contain is `disqualified` with `no_manifest_entry`, and symbol resolution for it reports `dependency_not_in_build`, scoped to that package. A project without trusted assets, a platform target such as `net8.0-android`, an assembly, script, `packages.config` or Paket file, or an MSBuild element or property restore doesn't model leaves the build open. The result is a fact about the checked-in build, with no MSBuild properties set by the CI environment or the command line (#176).
- Dependency loading and symbol resolution read the `<tfm>/<rid>` target restore wrote for the runtime the build's outputs name. When the outputs name no runtime or several, every package a runtime target adds or re-versions is a named miss scoped to its restore closure. A runtime restore wrote no target for is declared `reachability_undetermined:runtime_target_absent`, and no sink is searched (#244).
- The IL search models the shared framework. A call into an assembly the build's shared framework supplies (.NET Core 3.1 or later, read from `project.assets.json`) is a leaf, except reflection, dynamic loading, serializers, the DLR, name-based activation and any member taking a `Type` or runtime handle, which stay hazards. The framework's callbacks into application code, property accessors included, are searched as roots over the types the program instantiates. ASP.NET Core controller actions, Razor Pages handlers, compiled view bodies and delegates handed to Microsoft.AspNetCore APIs are search roots too; a path from one is a candidate and never grounds `not_exploitable`. ASP.NET Core and Microsoft.Extensions hosting assemblies are not framework leaves, so a hosted `Main` stays `undetermined` (#245).

### Report format

This release changes the Report's schema. A consumer that gates on `schema_version` sees `tegron.report.v3`.

- `schema_version` is `tegron.report.v3`. Reading a v2 or v1 Report upgrades it to v3, dropping a priority block that has no per-value stamp (#173).
- `priority.snapshot` is removed. Each value carries its own stamp: `epss_as_of`, `kev_catalog_version` and `kev_date_released`. `kev_listed` appears only when `true` (#167).
- `epss_score` is written whenever the finding has an EPSS value, a score of 0 included, and `epss_percentile` whenever the signals file sourced one, 0 included (#173).
- New optional fields: `provenance.intel.signals_digest`, the digest of the signals file the findings were ranked with (#167, #188); `provenance.intel.corpus_signer` (`identity`, `issuer`), set only when a corpus release signature was verified (#163); and `build_graph` on every Java and Kotlin scan, with `source` (`build_tool`, `build_tool_file` or `off`) and, when the graph could not be had, `cause` (`kind`, `detail`) (#165).
- New `undetermined_reason` value: `advisory_symbols_unvetted` (#162).
- New `evidence.basis` value: `vulnerable_symbol_unreachable`, for a `not_exploitable` whose search found no path to a symbol that is present in the build. It is valid only on `not_exploitable`. `package_not_loaded` carries it too; `vulnerable_symbol_absent` stays on the grounds that find the symbol absent (#270).
- New optional fields: `library_entrypoints`, one record per ecosystem of the entry-point set the scan used (#264), and `evidence.assumptions` on a `not_exploitable`, valid only there (#264). OpenVEX, SARIF and HTML state a refutation's assumptions (#264).
- Every JavaScript scan records `dependency_code` with its `source` (`fetch`, `offline` or `off`). A fetch that fails, in whole or in part, doesn't fail the run: the scan reads no dependency code, reports what `off` would, and names why in `dependency_code.cause` (`kind`, `detail`) and a `tool_failure:dependency_code_unavailable` partiality note. A malformed `-dependency-*` flag still fails it (#257).
- New partiality reasons from the Java and Kotlin lanes: `tool_failure:build_graph_absent` and `other_tool_build` (#165), `unlisted_install` and `dependency_not_in_build` (#171), and `dependency_not_in_build` from the .NET lane (#176).

### CLI

- `-advisory-signals` (env `ASSAY_ADVISORY_SIGNALS`) takes the EPSS/KEV signals file, `signals.json` or `signals.json.gz`. Without it the run uses the `signals.json` of an `-advisory-corpus` directory, when there is one. `-advisory-signals-max-age` (default 7 days) sets when the run summary warns that the file is stale; a stale file still loads (#167, #174).
- `-build-graph auto|<file>|off` (default `auto`) sets where a Java or Kotlin scan's dependency graph comes from: the repository's own Maven or Gradle, a graph written ahead of time by `resolve-graph`, or none. `-build-graph-tool auto|maven|gradle` (env `ASSAY_BUILD_GRAPH_TOOL`) picks the tool; `auto` fails when both builds sit at the repository root (#165).
- `-subject-java-version` and `-subject-maven-profiles` are now the graph's run conditions. Under `auto`, a build tool on another JDK major fails `jdk_mismatch`, profiles go to Maven as `-P`, and stating profiles for a Gradle build fails. A graph file must record the same statement (#165). The stated Java version is the JDK the program runs on, and must share the build JVM's major (#172).
- `resolve-graph` writes `assay.buildgraph/v2` and takes only `-tool`, `-profiles` and `-java-version`, besides `-dir` and `-out`; `-D` and `-env` are removed (#165). It refuses to write a graph that includes a Gradle build outside the checkout (#169).
- `-dependency-code off|fetch|offline` (env `ASSAY_DEPENDENCY_CODE`, default `fetch`) sets whether a JavaScript scan reads dependency code. `-dependency-cache` (env `ASSAY_DEPENDENCY_CACHE`) is the directory tarballs are verified into and read from, required for `offline`. `-dependency-timeout` (env `ASSAY_DEPENDENCY_TIMEOUT`, default 15m) bounds acquisition, and `-dependency-npmrc-env` (env `ASSAY_DEPENDENCY_NPMRC_ENV`) names extra variables a `.npmrc` `${VAR}` may read (#210, #217). `-dependency-uncredentialed-cache` (env `ASSAY_DEPENDENCY_UNCREDENTIALED_CACHE`) names a directory, separate from `-dependency-cache`, that receives only the packages fetched without credentials, for a caller that persists it (#257).
- The CLI and the Action read dependency code by default, fetching lock-pinned npm package tarballs from the registry the project configures (#257).
- `-library-entrypoints` (env `ASSAY_LIBRARY_ENTRYPOINTS`, default `auto`) takes `auto`, `none` or a list of paths relative to the repository root, such as `pkg/api,!pkg/api/internal`; a list of `!path` entries alone keeps `auto` for the rest. An unparsable value fails the run (#264).

- The `pr-inherit` summary prints an `assessed:` line naming the advisories the fast path assessed because the baseline held no row for them (#168).

### Action

- The corpus release route verifies the release's `bundles.json` with cosign (v3.1.3, pinned by sha256) against `bundles.json.sigstore.json` before it reads anything in it. The signer is the one you name in the new `corpus-signer-identity` and `corpus-signer-issuer` inputs, which have no default; Assay doesn't choose whose signature you trust. A missing input or signature, or a failed check, fails the run. The route also needs `github.com` and `tuf-repo-cdn.sigstore.dev` (#163).
- A new `dependency-code` input (`fetch`, `offline` or `off`; empty leaves the scanner's default) sets whether a JavaScript scan reads dependency code. Unless it is `off` or `persist-dependency-cache` is `never`, the Action restores and saves the fetched packages with actions/cache, keyed on the repository's lockfiles. A new `persist-dependency-cache` input (`auto`, `always` or `never`, default `auto`) sets what is saved; `never` saves nothing. Under `auto`, a private or internal repository saves every package, and a public repository, or one whose visibility is unknown, saves every package except those fetched with credentials, which are fetched again on each run (#257).
- The corpus release route also downloads the release's `signals.json.gz`, after the signature check, checks it against the sha256 the signed `bundles.json` names, and passes it to the scanner as `-advisory-signals`. A release that can't supply verified signals fails the run. With an `advisory-corpus` directory the Action passes nothing, and the directory's own `signals.json` applies (#177).

- A new `library-entrypoints` input (default `auto`) is passed to the scanner as `-library-entrypoints`; see "CLI" (#264).

### Before you upgrade

**Move your Action pin.** Workflows pinned to `@v0.5` or earlier keep fetching those releases. To get this one, use `uses: ferralon-ai/ferralon-assay@v0.6` (or `@v0.6.0`, or that tag's commit SHA). If you set `scanner-sha256`, update it to the v0.6.0 tarball's checksum. Leave `scanner-version` unset and the tag runs the v0.6.0 scanner. The Action gains five inputs: `library-entrypoints`, `dependency-code`, `persist-dependency-cache`, `corpus-signer-identity` and `corpus-signer-issuer`; see "Action".

**OpenVEX justifications change.** A `not_affected` statement for a reachability refutation now carries `vulnerable_code_not_in_execute_path` instead of `vulnerable_code_not_present`. `vulnerable_code_not_present` stays on refutations and disqualifications grounded on an absent symbol or an unaffected version. A `not_affected` with no basis that maps to a justification carries an `impact_statement` and no justification, and a refutation that stands under an assumption states it in the `impact_statement`. A consumer that matches on the justification string needs the new value (#270, #264).

**Pinning back to v0.5.x is a one-way door.** The Report schema is now `tegron.report.v3`, and v0.5.x can't read a state ref (`refs/assay/state`, or the `state-ref` you configured) written by v0.6. If a repository runs a v0.6 baseline and then pins back to `@v0.5`, every run fails on state read until the state ref is deleted, for example with `git push origin --delete refs/assay/state` (#173).

**The corpus release route needs a signer you name.** If you set `advisory-corpus-policy` with `advisory-corpus-repo`, and `advisory-corpus-ref` names a corpus release (the default `main` resolves to the latest one), set `corpus-signer-identity` and `corpus-signer-issuer` from the corpus's own consumer documentation. Without them the run fails. The runner must reach `github.com` and `tuf-repo-cdn.sigstore.dev` (#163).

**The corpus release must ship signals.** On the same route, the Action needs the corpus release to publish a signed `signals.json.gz`: its `bundles.json` must be `bundle_version` 1.1.0 or later and carry a `signals` object naming the file's sha256. A release without them fails the run, including a release read for a manifest-only policy. The scan step passes `-advisory-signals`, which a v0.5.x scanner doesn't define, so keep `scanner-version` on v0.6 or later (#177).

**A signals file must carry a matching `signals_digest`.** A file whose stated digest isn't the digest of its payload fails the run, as does one with a repeated key or keys that differ only in case. Regenerate a hand-edited or re-keyed signals file with its producer (#188).

**Expect fewer findings to carry a priority.** The scanner no longer ships EPSS or KEV data. A run that is given no signals file reports no priority on any finding. That includes a run with no corpus, and the Action's git fetch of a corpus by branch or commit, which doesn't fetch its `signals.json` (#167).

**Expect some CVE and GHSA rows to lose their priority.** A CVE-keyed advisory with no signals record of its own carries no priority. A GHSA or other advisory carries none when its only CVE record comes through a PYSEC, GO or RUSTSEC roll-up, or when its CVE aliases' records disagree (#174).

**Java and Kotlin scans run your build tool.** Under the default `-build-graph auto`, which is what the Action runs, the scan resolves dependencies with the repository's `./mvnw` or `./gradlew`, or `mvn` or `gradle` on `PATH`, using the job's environment and JDK. That runs the build's scripts and plugins, and the tool fetches from the repositories the build configures. The runner needs the tool, the JDK your build uses, and credentials for private repositories. A scan that can't resolve the graph publishes the Report and then fails the job, with the cause in `build_graph.cause`. On the CLI, `-build-graph off` scans without a graph and leaves JVM versions `undetermined` (#165).

**Regenerate saved build graphs.** A graph written by v0.5.x's `resolve-graph` is rejected as `graph_rejected:schema`. Write it again with this release's `resolve-graph`, and pass `-java-version` and `-profiles` matching what the scan states (#165).

**JavaScript scans fetch dependency code by default.** In the Action and on the CLI, a JavaScript scan reaches the registry your project's `.npmrc` configures and presents a token only to the host it names. Credentials come only from the project `.npmrc`, `NPM_CONFIG_USERCONFIG` and `NPM_CONFIG_REGISTRY`, and a `${VAR}` reference reads only `NODE_AUTH_TOKEN`, `NPM_TOKEN` and the names you add with `-dependency-npmrc-env`; a CI step that provides credentials should provide them through those. The Action caches the fetched packages keyed on your lockfiles, so an unchanged lock fetches only the packages it does not hold. Under the default `persist-dependency-cache: auto`, a public repository, or one whose visibility is unknown, never saves a package fetched with credentials, because a fork pull request's run can restore the default branch's cache, so those packages are fetched on every run; `persist-dependency-cache: always` saves them too. A fetch run takes longer and uses more memory than one without dependency code. Set the Action's `dependency-code: off`, or `-dependency-code=off`, to read no dependency code (#210, #217, #257).

**Expect some rows to change verdict.** Rows whose `not_exploitable` rested on the absence of an unvetted symbol list become `undetermined` (`advisory_symbols_unvetted`) (#162). Java and Kotlin advisories on packages a complete build graph doesn't install become `disqualified` (`no_manifest_entry`) (#171), as do .NET advisories on NuGet packages a closed build doesn't contain (#176). Java and Kotlin searches that used to stop at lambdas, string concatenation or `String` and boxed-value calls can now end in `not_exploitable` (#100, #172), as can Java searches that ran only through a dependency class that cannot link (#187, #196), and a dependency's copy of a JDK class no longer grounds one (#172, #181). Some Java and Kotlin rows that crossed an unopened dependency type or interface become `undetermined` (`unloaded_dependency`) or `reachable_candidate` where they were `not_exploitable` (#186), and some where a loaded override reaches the sink become `reachable_candidate` where they were `undetermined` (#193). Rows whose Go module is replaced in `go.mod` are judged on the replacement, so some Go rows that were `disqualified` on the required version become `reachable_candidate` or `undetermined` (#201). JavaScript and Python rows resting on a version a script command may install stay open, including every build a yarn install runs (#137, #224), while builds whose only install commands are the forms now allowed resolve their versions (#212, #213, #214, #215). JavaScript rows that were `undetermined` because no path reached the advisory's symbols can become `reachable_candidate` once dependency code is read by default, when a path traced through a read package reaches them, or `undetermined` (`advisory_range_absent`) with the path kept when the advisory has no range the version axis can bound (#257). Locks and pnpm layouts the lock readers can no longer vouch for are withheld, so JavaScript rows resting on them become `undetermined` (#231, #232), and a JavaScript load of a read package no longer withholds a row run-wide, so rows that were `undetermined` for `uninspectable_package` can resolve (#255). Python rows whose `pyproject.toml` holds dependency groups or tool tables, or whose build upgrades pip, resolve their versions where they were `undetermined` (#250, #254). .NET searches clear or find a path through shared-framework calls and ASP.NET Core entry points, and a package only a runtime target supplies is judged on that target (#244, #245).
Go refutations change in both directions. An undeclared scan (`library-entrypoints` `auto`) releases refutations where only `cmd`, `examples` or `test` libraries reach the module (#264). A module that merely reaches `reflect` no longer withholds every refutation, and a refutation is withheld when a call reflection makes, a finalizer, a file excluded by platform or tag, a standard-library file for another platform or a cgo variant that cannot be resolved could contradict it (#253, #256, #258, #260, #261, #262, #267, #269, #271). A standard-library advisory is no longer cleared against a two-part `go` line as a toolchain minimum (#266).

More Go findings are graded `attacker_tainted` and the credited entry point can differ, while verdicts are unchanged (#234).
The changes behind this are listed under "Verdicts and analysis".

**Coming from v0.4.x or earlier?** Read the v0.5.0 notes as well; their changes apply on top of these. One of them matters for anyone who reads Go reachability directly: when govulncheck has no evidence about an advisory (it doesn't know the advisory, disagrees that the version is affected, or never analyzed the module), Go reachability reports `advisory_unknown_to_analyzer` instead of a complete search, so the row is `undetermined` rather than refuted. That change shipped in v0.5.0 (#83).

**Parsing the Report?** It is not additive this time; see "Report format" (#167, #173).

### Breaking (library API)

This affects Go code that imports Assay as a module, and analyzer plugins built outside this repository. The CLI, Action and Report changes are under [Before you upgrade](#before-you-upgrade).

- `report.Priority` drops `Snapshot`, and `KEVListed` is omitted from JSON when false. Trigger runs no longer rank findings by themselves: a request ranks only with the `Signals` it is given, and a nil `Signals` reports no priority (#167).
- `report.SchemaVersion` is `tegron.report.v3`. `Upgrade` takes a v2 Report to v3 and drops a priority without per-value stamps (#173).
- `pipeline.WithSubjectJavaVersion`, `pipeline.WithSubjectMavenProfiles` and `AssessConfig`'s `SubjectJavaVersion` and `SubjectMavenProfiles` are removed, and the `java.version` and `maven.profiles` target-environment entries are no longer sent to plugins. State the Java version and profiles as the build graph's conditions instead (#165).
- `buildgraph.Schema` is `assay.buildgraph/v2`. `buildgraph.Load` rejects a v1 graph (#165).
- `projection.VEXJustNotReachable` is renamed `projection.VEXJustNotInExecutePath`, and its value is `vulnerable_code_not_in_execute_path`, the OpenVEX label (#270).
- The Kotlin plugin's capability manifest is 1.2.0. Its resolvers are `gradle` and `maven`, and the `gradle_version_resolution` boundary is gone (#165).

### Known issues

- **Installs run from inside a script.** A package that a script installs at install time, such as a `prepare` script that runs `node setup.js`, which in turn calls `npm install x`, is not seen, so it gets no findings. Because that is arbitrary code, there is no general fix; it does not change the verdict of any package that is seen.
- **JVM projects using Spring.** When Spring is on the classpath, rows that would otherwise be `not_exploitable` stay `undetermined`. The analysis withholds a verdict here and never clears one.
